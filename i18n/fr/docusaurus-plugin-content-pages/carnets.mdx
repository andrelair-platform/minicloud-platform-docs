## Comment un cas voyage

Un article de fond par sujet suffit. Le blog héberge l'article, [System Design](/system-design) permet de le
découvrir par question, et la documentation fournit le schéma de référence. Le même cas est ensuite décliné
par canal :

| Format | Ce que je partage |
|---|---|
| **Blog** | Le raisonnement complet — ce que je protège, pourquoi une copie locale, ce qu'apporte une copie hors site, et les restaurations que j'ai réellement testées. |
| **Newsletter** | Le récit. *« Si les machines qui hébergent mes applications deviennent inaccessibles, est-ce que je peux encore récupérer leurs données ? »* — puis comment cette question a guidé le choix. |
| **LinkedIn** | Une question et une idée. *« Si toutes mes machines deviennent inaccessibles, où est ma sauvegarde ? »* — puis le critère et un lien vers le cas. |
| **À l'oral** | *« Je veux pouvoir récupérer mes données même si je perds l'accès aux machines qui font tourner mes applications. Une copie hors site couvre ce scénario. Ensuite, je dois vérifier que je peux vraiment restaurer les données. »* |

Pour un choix hybride, je précise toujours **ce que j'exploite moi-même, ce que je délègue et pourquoi** —
ces responsabilités concrètes donnent du sens aux mots *open source*, *auto-hébergé* et *service cloud managé*.
