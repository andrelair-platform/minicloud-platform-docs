# Documentation Standard — what docs exist, where they live, when they're required

:::note Map + pointer
This is the **single view** of the platform's whole documentation system — the FAANG documentation
taxonomy (Product · Architecture · Developer · API · Quality · Operations · Security/Compliance ·
Business/Lifecycle · AI) **mapped onto the homes that already exist here**, path-gated like the delivery
paths. The decision of record is the rule
[`.claude/rules/documentation-standard.md`](https://github.com/andrelair-platform/minicloud-gitops/blob/main/.claude/rules/documentation-standard.md);
this page is its published map. Companion: the writing **discipline** (docs-as-map, verified-reality, the
Definition-of-Done gate) lives in
[`documentation.md`](https://github.com/andrelair-platform/minicloud-gitops/blob/main/.claude/rules/documentation.md).
:::

## Two axes first (don't flatten them)

1. **Platform vs IS** — a doc belongs to the **Platform** pillar (a shared capability, one copy) or the
   **IS** pillar (a business app, docs live with the product). See the pillar boundary in the
   [Architecture Hub](/platform/architecture).
2. **Delivery path (A/B/C)** — the doc burden scales to the work, exactly like the SA artefact set: a
   one-line fix writes ~nothing new; a new product produces the full set.

**We do not impose a generic `docs/01-07/` tree** — it would duplicate the SA artefact set and fight the
docs-as-map model. The taxonomy is a **path-gated checklist pointing at existing homes**, plus one
canonical per-product skeleton (below).

## New practice 1 — requirement IDs + the traceability matrix (the enterprise signal)

Give every requirement a **stable, observable** ID (`FR-###` / `NFR-###` / `SEC-###` / `AI-###`) and thread
it **requirement → architecture component → test file → pipeline stage → evidence** in one matrix. It
answers the question that separates mature engineering from "it works on my machine":

> *If `SEC-001` changes tomorrow, which components, tests, pipelines and docs must change?*

Template:
[`docs/templates/traceability-matrix.md`](https://github.com/andrelair-platform/minicloud-gitops/blob/main/docs/templates/traceability-matrix.md).
**Worked reference (real IDs, real tests, real CI):**
[`ktayl-core/docs/traceability-matrix.md`](https://github.com/andrelair-platform/ktayl-core/blob/main/docs/traceability-matrix.md)
— note it also *surfaces the requirements not yet tested*, which is precisely the point of the exercise.

## New practice 2 — the canonical per-product `docs/` skeleton

One reconciled layout (SA artefact set + the category checklist, platform concerns linked not copied), so
products stop varying. Full tree:
[`docs/templates/product-docs-skeleton.md`](https://github.com/andrelair-platform/minicloud-gitops/blob/main/docs/templates/product-docs-skeleton.md).
Reference products: **ktayl-core** (plain `docs/`) and **retrieva** (Docusaurus).

## How a developer uses this

- **Starting a product?** Follow the [zero→prod runbook](/platform/app-deployment/new-business-service); it
  already seeds the skeleton. For a Path-C product, produce the full SDD + the traceability matrix.
- **Making a change?** Pick the delivery path → the table tells you which docs to touch; update them in the
  **same PR** (the Definition-of-Done gate, per `documentation.md`).
- **Looking for a doc?** The central site is the map: ADRs → [decision records](/platform/engineering-standards/decision-records),
  schemas → [ERD index](/is/insurance-platform/schema-erd-autogenerated), tests → [testing strategy](/platform/engineering-standards/testing-strategy).
