# System Design

Three angles on the same platform, each answering a different design question:

- **Hybrid Infrastructure** — *where* a service runs (my hardware vs. a managed cloud service), and why.
- **Developer Platform** — *how* an application is delivered and operated.
- **Insurance Information System** — *how* a business process is designed.

Every case below follows the same thread — **Problem → Consequence → Choice → Trade-off → Verified** —
and, for a hybrid choice, names **what I operate myself, what I delegate, and why**. Each card is a short
frame; the full reasoning lives in the linked write-up on the [Blog](/blog), and the reference diagram
in the docs.

## Hybrid Infrastructure

### Why keep one backup on my hardware *and* one off-site?

- **Problem** — I already mirror backups to Cloudflare R2. So why keep a MinIO server running on the
  controller at all? Couldn't I retire it and go cloud-only?
- **Consequence** — Cloud-only means a single operational domain. One fat-fingered delete, one credential
  leak, one provider lockout, and the backup and its only copy can fail together.
- **Choice** — Keep a local MinIO **and** an off-site copy in R2. Local gives fast, sovereign restores;
  off-site survives losing the whole site. I **operate** the MinIO server; I **delegate** durable off-site
  storage to R2 — because an off-site copy is exactly the risk a managed service covers best.
- **Trade-off** — A second store to run and reconcile, in exchange for a restore path that survives either
  layer failing.
- **Verified** — An hour after reasoning this through I deleted the wrong bucket prefix — and the design
  held: the other copy restored it.

## Developer Platform

### When does a person validate a release?

- **Problem** — I want continuous delivery, but not every change should reach production unseen. Where does
  a human step in?
- **Consequence** — Automate everything and a bad change ships itself; gate everything and delivery stalls
  under manual toil.
- **Choice** — Automatic deploy to the **dev** environment, then a **human-approved** promotion to prod.
  **Kargo** promotes one immutable image by opening the Git change; **Argo CD** reconciles it. The approval
  lives in Git (a CODEOWNERS-gated PR), so continuous reconciliation is never broken.
- **Trade-off** — One deliberate human gate on the prod path, in exchange for a safe, auditable promotion
  instead of a hand-edited image tag.
- **Verified** — The delivery flow runs on every custom service; a dev promotion auto-merges, the prod PR
  waits for review.

## Insurance Information System

### How do I check that what was billed matches what was booked?

- **Problem** — An auditor asks a simple question: *does the ledger agree with what you billed this month,
  and can you prove it?*
- **Consequence** — Without a reconciliation step, a premium can be invoiced but never posted to the general
  ledger — and nobody notices until it's a year-end problem.
- **Choice** — A finance close that walks each premium from invoice to the general ledger, compares the
  amounts, and surfaces any gap — with an append-only audit record. The period "close" is a control, not a
  physical lock.
- **Trade-off** — The close can't *physically* freeze the ledger without breaking the architecture; instead
  it detects and flags any post-close movement — honest over absolute.
- **Verified** — Shipped to the dev environment; the reconciliation flags a mismatch and the close record is
  immutable.
